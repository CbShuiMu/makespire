# 杀戮尖塔 2 模组制作

把自然语言或 JSON 设计落实为目标工程内的代码、本地化和资源，验证可用的构建与运行环节。默认中文沟通，保留代码符号原文。BaseLib 特指 [Alchyr/BaseLib-StS2](https://github.com/Alchyr/BaseLib-StS2)。

## 先判断工程与证据

1. 读取目标工程的说明、`.csproj`、构建 props/targets、manifest、初始化入口和同类内容。区分新建、增量修改、旧模板迁移和问题排查；不要为增加一张牌重建整个工程。
2. 记录游戏版本及分支、实际引用的 `sts2.dll`、BaseLib 编译依赖与运行时版本、.NET SDK、MegaDot/Godot 版本。先证实兼容性，再决定是否升级；网页当前版本不能代替目标工程版本。
3. 使用 `scripts/inspect_mod.py <工程目录>` 做只读盘点。脚本不执行构建、不读取 `.env`，也不证明 MSBuild 属性已求值或资源已正确加载。
4. 本机参考工程为 `E:\JellyProject\sts2_mod_agent`；不可用时接受用户提供的路径，或使用目标游戏源码与上游文档。使用它时读 [本地流程与检索](references/local-workflow.md)，无需为了用本技能启动整个 Flask/Milvus 系统。

**证据优先级：**目标游戏 DLL/同版本源码与实际安装的 BaseLib → 已验证的目标工程实现 → 对应版本上游源码/文档 → 其他教程。反编译缓存与 RAG 索引可能过期。没有查到 API 表示“尚未确认”，不能直接判定需求无法实现。

## 从需求到实现

### 1. 建立对象与效果清单

从文字/JSON 提取对象类型、稳定类名、触发时机、目标、数值、升级、归属池及资源需求。缺少影响机制方向的信息才提问；普通命名、布局沿用工程惯例。

将复合效果拆成原子子句，保留对象归属与触发上下文。按作用对象检索，例如遗物的“拾起时”查 relics，“升级牌组中的卡牌”查 cards。卡牌施加 Power 时，分别确认 Card 和 Power 的结构与生命周期。

### 2. 找同类实现，核对调用链

有可用 RAG 时依 [本地流程](references/local-workflow.md) 查询；否则在本地化中找原版对象，再定位 `.cs`。已知路径批量读取，已知类型查精确文件，避免反复全树搜索。

核对类型、命名空间、构造函数、重载、可见性、异步返回值和生命周期签名。查看效果调用的 Commands、Power 与基础 Model，不只看卡牌文件。对每个新机制保留可追溯的文件/符号或上游链接；共享 API 可复用已核实证据。

反编译器产生的 `_003C...` 辅助类、状态机等不能直接复制，改写为普通 C# 集合与 async/await。证据不足时继续定向查证；只有语义等价时才采用替代 API，不静默改变需求。

### 3. 选择模板与扩展点

新建内容/角色模组优先使用兼容的 Alchyr 模板；已有工程沿用其基类与资源约定。依赖、注册、模型及本地化见 [BaseLib 实现约定](references/baselib.md)。

优先用 Commands、Model 覆写及 BaseLib 扩展点；修改原版流程且没有合适扩展点时再用 Harmony。补丁须匹配确切类型、重载和执行时机。不得把 STS1 的 Java API、事件名或注册流程当作 STS2 API。

### 4. 完成代码、注册、本地化与资源

每个对象形成闭环：效果代码 → 注册/池归属 → 本地化 → 图像/场景引用 → 升级和边界行为。使用项目自定义基类，避免绕过已有资源路径或 ID 处理。

数值显示与逻辑使用同一套动态变量；检查 Owner、触发来源、目标合法性、重复触发和模型可变状态。涉及随机数、玩家选择或联机状态时，沿用同版本原版 RNG、choice context 和命令流程，不使用任意本地随机或 UI 回调直接改共享状态。

合并写入本地化 JSON，保留无关条目；使用真实 Model ID/分析器生成的键，不能一概套用裸类名。资源应有实际文件或明确的临时素材，不能只写不存在的路径。不要为了补一张图打包整套原版资源。

### 5. 分层验证与交付

按 [构建与验证](references/build-test.md) 核查静态内容、编译、资源包和游戏内行为。`dotnet build` 不等于资源已更新；某些模板导出错误只报 warning，退出码为 0 也不能证明 PCK 成功。

Windows 上每批实际模组工程写入完成后，默认由 Agent 执行 `python scripts/verify_mod.py <模组工程目录>`，自动发现 Steam 游戏、缓存匹配版本的 MegaDot、编译并导出、挂载 PCK 和调用原版 ModManager 检查初始化。读取 `report.json` 和失败阶段的日志，修复任务范围内的代码或配置问题后重跑，用户无需打开编辑器或执行命令。具体支持范围及加载探针限制见构建参考。仅有创作设定 JSON 时，先完成真实工程生成再验证。

一轮完成用户已要求的全部对象，不默认套用旧项目的“每对象等待继续”模式。只有用户明确选择逐个确认时才分轮。

交付说明修改文件、依赖版本、执行过的验证、产物位置与未验证环节。缺少游戏环境时完成可做的代码/静态检查，给出具体运行步骤；不能声称游戏内测试通过。制作模组不自动包含 Workshop 上传。
